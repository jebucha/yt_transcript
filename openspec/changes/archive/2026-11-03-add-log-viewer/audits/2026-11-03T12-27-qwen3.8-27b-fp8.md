### Findings

| AC-1 | Accuracy | Warning | Proposal claims base requirements change, but the delta only adds new requirements | proposal.md "Modified Capabilities": *"the 'Fetch operation logging' and 'Persistence operation logging' requirements change"*. But `specs/structured-logging/spec.md` contains only `## ADDED Requirements` ("Fetch failure detail", "Save failure detail") — no `## MODIFIED Requirements` section. On archive, the two named base requirements remain textually unchanged; the delta's end state is functionally sufficient, but the proposal's account of what changes is inconsistent with the delta structure. |
| AC-2 | Accuracy | Warning | `detail=exc.message` hint is wrong for 2 of the 3 failure branches | Design decision 5 and task 3.1 both say to add `detail=exc.message` to "the three failed `fetch_attempt` log calls". In `app/chain.py` L98–111 the timeout branch's `exc` is `asyncio.TimeoutError` (built-in, no `.message` attribute) — a literal `exc.message` raises `AttributeError`; the message T-STRUCTURED-LOGGING-012 requires (with duration) is on `timeout_err.message` (L99–101). In the generic branch (L112–125) the meaningful message is on `generic.message`; the raw `exc` message may be empty. Task 3.1's own verification would catch this, but the hint contradicts the spec scenario and the code. |
| AC-3 | Accuracy | Info | Design Context overstates which modules log from worker threads | design.md Context: *"app/chain.py and app/persist.py log from worker threads (asyncio.to_thread)"*. In `app/chain.py` only the fetcher *call* runs in a worker thread (`asyncio.to_thread(func, …)`, L84); all `fetch_attempt` log calls (L88–125, L129–137) execute in the coroutine on the event loop. Only `app/persist.py` genuinely logs from a worker thread (`save_transcript` via `asyncio.to_thread`, main.py L99–101). Design decision 3's thread-safety requirement remains justified via persist.py. |
| FS-1 | Feasibility | Warning | "Forwards to the real sys.stdout" is ambiguous against existing capsys-based tests | Design decision 2: TeeStream `write()` *"forwards each complete line to the real `sys.stdout`"*. But `tests/test_logging_requests.py` L17–25 calls `setup_logging()` with no argument and asserts log lines land in `capsys.readouterr().out` (comment: *"resolves sys.stdout at logger-creation time (captured)"*). If the tee binds the original stdout (import-time or `sys.__stdout__`), these tests capture nothing and task 1.2's verification ("`test_logging_requests.py … still passes unchanged`") fails. The design should pin that the tee resolves the *current* `sys.stdout` (at write time, or when `setup_logging()` is called without an explicit stream), matching the lazy resolution it itself describes in Context. |
| CM-1 | Completeness | Info | Integration tasks have no direct spec requirement | tasks.md 5.1–5.4 (full non-e2e suite, full e2e suite, manual smoke test, test-requirement cross-check) are verification tasks with no individual requirement mapping. Expected for integration verification; noted for completeness. |
| VL-1 | Validity | Info | design.md has no `## Test Strategy` section | design.md sections: Context, Goals/Non-Goals, Decisions, Risks/Trade-offs, Migration Plan. Test Requirement blocks carry full Commands directly (consistent with base-spec blocks and the repo's `python -m pytest …` convention), but per the audit convention blocks reference a `## Test Strategy` section rather than repeating runner/environment details. Single finding per change. |
| VL-2 | Validity | Info | Buffer/display cap values are pinned in design only, not in the spec | `specs/log-viewer/spec.md` "Log history replay": *"capped at a bounded number of the most recent entries"*; "Panel display cap": *"the panel's display cap"*. The value (200) appears only in design decisions 3 and 6. Behavior is testable, but T-LOG-VIEWER-005/016 will assert against an implementation constant rather than a spec-stated value. |
| CO-1 | Coherence | Info | New unauthenticated read surface: full log stream | `GET /api/logs` delivers every server log entry (transcript file paths, OS error strings, request method/path/status) to any client with no authentication. Consistent with the app's existing unauthenticated read endpoints (`/api/transcripts*`) and with the base "No sensitive data in logs" requirement (T-STRUCTURED-LOGGING-009) constraining log content; noted for security-surface awareness, not a blocker. |
