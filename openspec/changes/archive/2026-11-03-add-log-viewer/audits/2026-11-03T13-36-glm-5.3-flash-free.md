| VL-2 | Validity | Info | Buffer/display cap values are pinned in design only, not in the spec | `specs/log-viewer/spec.md` "Log history replay": *"capped at a bounded number of the most recent entries"*; "Panel display cap": *"the panel's display cap"*. The value (200) appears only in design decisions 2/3 and 6. Behavior stays testable, but T-LOG-VIEWER-005/016 will assert against an implementation constant rather than a spec-stated value. |
| VL-3 | Validity | Info | Spec's "known event types" list is narrower than the design's formatter map | `specs/log-viewer/spec.md` "Humanized log entry display" names known types as "(server lifecycle, HTTP request, fetch attempt, transcript save)", while design decision 6 and task 4.2 give a dedicated format to 8 events including `fetch_rejected` and `unhandled_exception`. `fetch_rejected` does not obviously fall under "fetch attempt", so the dedicated formatter arguably contradicts the spec's fallback rule for events "without a dedicated format". Behavior is still testable; wording could be aligned. |
| FS-1 | Feasibility | Warning | "Forwards to the real sys.stdout" is ambiguous against existing capsys-based tests | Design decision 2: TeeStream `write()` *"forwards each complete line to the real `sys.stdout`"*. But `tests/test_logging_requests.py` L17–25 calls `setup_logging()` with no argument and asserts log lines land in `capsys.readouterr().out` (comment: *"resolves sys.stdout at logger-creation time (captured)"*). If the tee binds the original stdout (import time or `sys.__stdout__`), these tests capture nothing and task 1.2's verification ("`test_logging_requests.py … still passes unchanged`") fails. The design should pin that the tee resolves the *current* `sys.stdout` at write time (or at logger creation), matching the lazy resolution it describes in Context. |
| FS-2 | Feasibility | Warning | Per-connection blocking queue reads tie up executor threads; disconnect path unspecified | Design decision 3: each SSE async generator reads its subscriber queue "by blocking in an executor (`asyncio.to_thread`)". `queue.Queue.get()` without a timeout blocks indefinitely, so every connected tab holds one default-executor thread (size ≈ min(32, cpu+4)) for the connection's lifetime — the same executor the app uses for `save_transcript`, `list_transcripts`, `read_transcript` (main.py L99, L116, L129). A disconnect cannot cancel a blocked `get()`, so the `finally` unsubscribe (decision 3, Risks) only runs after the blocked read returns; with a plain `get()` that never happens. The design should specify a poll-timeout loop (e.g. `get(timeout=…)`) for cancellation, and ideally bound concurrent SSE connections relative to shared executor usage. |
| FS-3 | Feasibility | Info | Snapshot-then-subscribe race can drop entries on first connect | Design decision 4: the generator "first flushes the ring buffer oldest→newest, then streams live entries". If subscribe happens after the snapshot, entries logged between the two steps are lost even on the first connect; if before, already-snapshotted entries are re-delivered (which the design accepts only as a reconnect trade-off). A one-line ordering rule (subscribe first, accept the small duplicate window, or track the snapshot boundary) would remove the ambiguity. |
| CO-1 | Coherence | Info | New unauthenticated read surface: full log stream | `GET /api/logs` delivers every server log entry (transcript file paths, OS error strings, request method/path/status) to any client with no authentication. Consistent with the app's existing unauthenticated read endpoints (`/api/transcripts*`) and the base "No sensitive data in logs" requirement (T-STRUCTURED-LOGGING-009) constraining log content — and the design explicitly handles XSS via `textContent` with a dedicated scenario (T-LOG-VIEWER-017). Noted for security-surface awareness, not a blocker. |
