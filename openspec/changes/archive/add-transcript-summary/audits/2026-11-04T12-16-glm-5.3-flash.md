| AC-1 | Accuracy | Warning | Spec validation-order wording conflicts with design decision 8, and rejection precedence is undefined for a combined failure | specs/transcript-summarization/spec.md "Summarize endpoint" requirement: "Local rejections (invalid name, unknown provider or model, oversized text) SHALL happen before **any filesystem access** or backend call". Design decision 8 reads the provider config file (filesystem access) at step 2, *before* the provider/model-id check (step 3) and the 100k-char text check (step 4). Also undefined: when the config is missing **and** text is overlong, does the request get 503 `NOT_CONFIGURED` or 400 `INPUT_TOO_LONG`? Either soften the requirement wording (e.g. "before any transcript-directory filesystem access") and pin the precedence, or reorder the input-cap check ahead of the config read. |
| AC-2 | Accuracy | Info | Terminology drift: `TRANSCRIPTS_DIR` vs `TRANSCRIPT_DIR` | proposal.md L16 says env vars follow "the existing `TRANSCRIPTS_DIR` pattern"; design.md Context L12 says the same. The *app* env var is `TRANSCRIPT_DIR` (singular — app/persist.py L77, Dockerfile `ENV TRANSCRIPT_DIR=/transcripts`); only the compose host-side override is spelled `TRANSCRIPTS_DIR` (docker-compose.yml `"${TRANSCRIPTS_DIR:-/home/john/transcripts}:/transcripts"`). Both spellings are real but refer to different layers; citing `TRANSCRIPTS_DIR` as *the* pattern when introducing `PROVIDERS_CONFIG` (an app-read env var) can mislead the implementer into thinking app-side env vars use the plural spelling. Canonical form for app-read env vars: `TRANSCRIPT_DIR`. |
| VL-1 | Validity | Info | design.md has no `## Test Strategy` section | design.md sections are Context / Goals-Non-Goals / Decisions / Risks / Migration / Open Questions. Test-requirement blocks are present and complete in all spec deltas, so this is a structural observation only (one per change per the audit convention). |
| CO-2 | Coherence | Info | Unprefixed task shorthand `(T-010)` is ambiguous across capabilities | tasks.md 3.4 refers to `test_output_is_clean_plain_text` as "(T-010)" (= `T-TRANSCRIPT-RETRIEVAL-010`), while tasks.md 2.1 refers to `test_summarize_sends_chat_completions_shape` as "(T-010)" (= `T-TRANSCRIPT-SUMMARIZATION-010`). | FS-2 | Feasibility | Info | No TLS note for remote plain-HTTP provider endpoints carrying bearer keys | Design decision 1 attaches `Authorization: Bearer <apiKey>` whenever a provider defines one, and `baseURL` is validated only as "in the config file" (decision 7) — nothing requires https.
