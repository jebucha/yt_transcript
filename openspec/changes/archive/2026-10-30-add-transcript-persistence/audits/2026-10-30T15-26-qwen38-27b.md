| AC-1 | Accuracy | Warning | Catch scope in the design is narrower than the spec's best-effort guarantee. The spec requires that a missing/unreadable/unwritable directory "or any other write error" SHALL NOT change the HTTP response, but the design's `save_transcript` catches only `OSError`. A non-`OSError` write failure (e.g. `UnicodeEncodeError` from a lone surrogate in a transcript or title) would escape `save_transcript`, propagate through the `asyncio.to_thread` call in the endpoint, and turn a 200 into a 500 — violating the best-effort requirement. Widen the catch (e.g. `except Exception`) or justify the narrow scope. | spec.md L94 vs design.md L45 ("catches `OSError`")/L49; tasks.md §2.1 ("on `OSError`") |
| AC-2 | Accuracy | Warning | Normative clause in "Overwrite on re-fetch" has no scenario. The requirement states "Distinct videos whose titles derive the same file name are not disambiguated; the most recent write wins," but the single scenario (re-fetch replaces the file) covers only re-fetching the *same* video. The design (L64) relies on this last-write-wins behavior as "spec'd," yet it is untestable as delta'd. | spec.md L81-91; design.md L64 |
| VL-1 | Validity | Warning | The "Title-based file name" requirement is internally contradictory and therefore non-testable as written. It says "removing all punctuation" and then "replacing each remaining run of whitespace or other non-alphanumeric characters with a single underscore." Applied literally in order, `Foo/Bar: The Story` → `foobar_the_story.txt`, contradicting the scenario's expected `foo_bar_the_story.txt` and the design's decision 3 (all non-alnum runs → `_`). | spec.md L31 vs L42-44; design.md L36 |

- Task ordering is buildable (persist.py derivation → writer → endpoint integration → deployment → verification) with no forward dependencies.

### Verdict
Can proceed with caution. Consider resolving warnings AC-1 (widen the catch or justify it), AC-2 (add a scenario for the distinct-video overwrite clause), VL-1 (fix the contradictory derivation wording), and VL-2 (align the path-separator scenario with its test) before or during `/opsx-apply`.
