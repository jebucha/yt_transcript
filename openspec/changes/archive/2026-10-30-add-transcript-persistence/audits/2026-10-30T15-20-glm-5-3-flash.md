### Findings

| ID | Category | Severity | Description | Evidence |
|----|----------|----------|-------------|----------|
| AC-1 | Accuracy | Warning | Design's catch scope is narrower than the spec's best-effort requirement. `specs/transcript-persistence/spec.md` L94 requires that "the transcript directory missing, unreadable, or unwritable, **or any other write error**" SHALL NOT change the HTTP response, but design decision 4 (design.md L45) specifies `save_transcript` "catches `OSError`" only. Non-`OSError` write failures (e.g. `UnicodeEncodeError`, a `ValueError`, if a transcript contains lone surrogates) would escape `save_transcript`, propagate through the `asyncio.to_thread` call in the endpoint (design.md L49), and turn a 200 response into a 500 — violating the spec. Design or tasks should widen the catch (e.g. `except Exception`) or justify the narrower scope. | spec.md L94 vs design.md L45/L49; task 2.1 also says "logs ... on `OSError`" |
| AC-2 | Accuracy | Warning | Normative clause in the "Overwrite on re-fetch" requirement has no scenario. The requirement (specs/transcript-persistence/spec.md L82) states "Distinct videos whose titles derive the same file name are not disambiguated; the most recent write wins," but the only scenario (L84–91) covers re-fetching the *same* video. There is no scenario/test for two different videos with identical derived names. Design.md L64 cites the "last write wins is spec'd" behavior, yet it is untestable as delta'd. | spec.md L81–91; design.md L64; tasks.md has no task for it |
| AC-3 | Accuracy | Info | Terminology drift: `TRANSCRIPT_DIR` (app env var, proposal L9, spec L106) vs `TRANSCRIPTS_DIR` (compose host-mount override, proposal L14, task 4.2). Intentional per design decision 6, but the single-letter difference between a container var and a host `.env` var is easy to conflate during implementation and ops; consider a README table or lighter separator. | proposal.md L9 vs L14; design.md L53 vs L55; tasks.md 2.1 vs 4.2 |
